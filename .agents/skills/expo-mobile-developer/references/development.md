# Development and release

## Setup and native integration

- For a new project, select a supported Expo template and TypeScript setup suited to the requested SDK, navigation, and preview target. In an existing project use its scripts and lockfile, install compatible Expo dependencies with `npx expo install`, and use `npx expo-doctor` for compatibility diagnostics. Check native libraries and config plugins against the actual SDK and architecture before selecting them.
- Determine whether native projects are generated by Continuous Native Generation or maintained by hand. In a generated project express durable native changes in app config or config plugins. In a maintained project apply and review platform diffs directly. Rebuild the development client after native dependency or configuration changes. Metro reloads JavaScript during development.
- For device connection issues, check the chosen client, SDK compatibility, Metro logs, and LAN reachability first. Use the project's supported tunnel workflow if the network prevents direct access. For native failures collect the relevant Android or iOS logs and reproduce using the closest available build and device.
- Use the existing navigation model. Check deep links from a cold launch and from an already running app, back behavior, and routes gated by auth. Test configurations involving app links, push, background tasks, or signing-linked capabilities on suitable native builds and devices.

## Implementation

- Separate server cache, navigation state, form state, and device persistence according to their lifetimes. Handle offline recovery, cancellation or stale responses, expired sessions, and duplicate submissions when the feature can encounter them. Scope and clear user-specific caches at the appropriate account boundary.
- Keep credentials out of client bundles and public environment variables. Use platform-appropriate secure storage for sensitive user credentials and ordinary persistence for non-sensitive data. Request device permissions when the feature needs them and cover denial, revocation, and settings recovery. Avoid logging secrets or personal data.
- Measure startup, scrolling, memory, and responsiveness on a representative physical device in a release-like build. Virtualize long lists, use stable keys, size images to their display needs, and profile expensive work before applying memoization or moving work across threads.
- Cover business rules and data transformations with targeted tests. Exercise component behavior through accessible user actions. Run the repo's lint, types, and test scripts, then verify affected flows on iOS and Android with the existing end-to-end harness or repeatable device steps. Include backgrounding, interruptions, and network failures when relevant.

## Distribution

- Confirm app identity, signing, build and version numbering, environment settings, and platform-specific entitlements with the existing release setup. Verify touched permissions, privacy disclosures, and store requirements against current official guidance.
- Smoke-test an internal or preview binary before staged distribution. Check production configuration, startup, auth, deep links, and changed device capabilities. Record build identifiers and track crash, startup, and journey metrics using the app's existing observability. Follow the rollout and recovery guidance in [legacy upgrades](upgrades.md) when a release changes runtime or stored data.
